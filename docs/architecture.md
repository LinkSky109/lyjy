# 系统架构设计

## 一、模块划分

| 模块 | 职责 | 状态 |
|------|------|------|
| market-data | 行情接入、清洗、存储、分发 | P0 |
| order-management (OMS) | 订单全生命周期管理 | P0 |
| execution (EMS) | 柜台对接、订单路由、算法交易 | P0(CTP) / P1(多柜台) |
| risk-control | 事前/事中风控、黑白名单、止损 | P0 |
| fund-management | 资金冻结/解冻、账户管理、清算 | P0(基础) / P1(清算) |
| backtest-engine | tick级回测、撮合模拟、成本模型 | P0 |
| strategy-sdk | Python策略开发工具包 | P0 |
| portfolio | 组合管理、再平衡、风险预算 | P1 |
| compliance | 监管报送、异常交易、AML | P2 |

## 二、核心数据流

### 2.1 行情流
```
行情源(CTP) → 行情接入服务 → 数据清洗 → Kafka(行情Topic)
                                          ↓
                              ┌───────────┴───────────┐
                              ↓                       ↓
                         ClickHouse存储         策略消费(实时)
```

### 2.2 交易流
```
策略信号 → 事前风控校验 → OMS订单创建 → EMS柜台报单 → 成交回报
                                                          ↓
                                                    持仓/资金更新
                                                          ↓
                                                    事中风控监控
```

### 2.3 资金流
```
订单报出 → 资金冻结 → 成交 → 资金扣减/持仓更新 → 日终清算对账
撤单 → 资金解冻
```

## 三、接口设计原则
- REST API：管理类操作（策略管理、账户查询、报表）
- Kafka事件：实时数据（行情、订单、成交）
- WebSocket：前端实时推送（持仓、盈亏、订单状态）

## 四、容错设计
- 订单幂等：订单号全局唯一，防止重复下单
- 资金冻结：报单即冻结，防止透支
- 故障隔离：单策略崩溃不影响核心交易
- 降级预案：行情源故障自动切换，系统过载自动限流
