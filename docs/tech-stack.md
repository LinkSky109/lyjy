# 技术选型 - 企业级量化交易平台

## 一、整体架构

```
┌─────────────────────────────────────────────────────────────┐
│                      策略层 (Python SDK)                      │
│  用户策略开发 / 回测 / 仿真 / 实盘                            │
├─────────────────────────────────────────────────────────────┤
│                    核心服务层 (Java/Spring Boot)              │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐       │
│  │ 行情接入  │ │ 交易执行  │ │ 风控引擎  │ │ 资金管理  │       │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘       │
├─────────────────────────────────────────────────────────────┤
│                    中间件层                                   │
│  Kafka(事件驱动) │ Redis(缓存) │ Nacos(配置)                 │
├─────────────────────────────────────────────────────────────┤
│                    数据存储层                                 │
│  PostgreSQL(交易/持仓/资金) │ ClickHouse(行情时序)            │
└─────────────────────────────────────────────────────────────┘
```

| 层级 | 技术 | 版本 | 用途 |
|------|------|------|------|

| 配置中心 | Nacos | 2.x | 动态配置、服务发现（P1引入） |

| CI/CD | GitHub Actions | - | 自动化构建测试 |
| 构建工具 | Maven | 3.9+ | Java项目构建 |

## 三、关键技术决策

### 3.1 为什么核心用Java而非C++？
- P0阶段优先跑通业务闭环，Java开发效率更高
- 用户团队为Java技术栈，维护成本低
- P2阶段如需微秒级延迟，可将核心交易链路用C++重构，通过JNI/IPC对接
- Java 17 + 虚拟线程可支撑万级TPS，满足P0/P1需求

### 3.2 为什么行情用ClickHouse？
- 列式存储，行情数据写入吞吐高（百万行/秒）
- 支持向量化查询，回测时历史行情扫描快
- 支持时间分区、TTL，适合时序数据
- 兼容SQL，学习成本低

### 3.3 为什么用Kafka？
- 行情分发：一份行情多策略消费，天然支持发布订阅
- 事件驱动：订单、成交、风控事件异步处理，模块解耦
- 可回溯：支持消息回放，便于问题排查和策略复盘

## 四、性能目标（P0阶段）
- 订单处理TPS：≥500
- 行情订阅标的：≥1000
- 风控校验延迟：<1ms
- 系统可用性：99.9%
